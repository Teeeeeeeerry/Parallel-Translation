# 站点页面规则改为数据,compat.ts 退为代码层

[src/dom/compat.ts](../../src/dom/compat.ts) 原本的定位是「兜底层,不是主路径」:每加一条域名补丁都被视为通用逻辑的缺陷,补丁写成 TS 代码,只有开发者能改。为了在特定网页上做到专业化翻译,本项目决定让站点页面规则成为一条正式路径:规则改为按域名匹配、以选择器描述的数据;内置规则随扩展打包,用户可以在设置页新建或覆盖。compat.ts 保留下来,只承载选择器表达不了的逻辑(例如 `take` 改指、favicon 尺寸的角标检测),不再是站点定制的主要写法。

第一期规则支持三项能力:排除(不翻译)、保留原文(嵌在句中但不翻译,即现有的 preserve)、限定范围(只翻译指定元素)。块级与行内修正会牵动 walker 的核心判定,暂不支持。

## 备选方案

- **维持现状,只在代码里多加站点** —— 实现成本最低,也符合原来的“兜底”原则,但用户遇到翻错的站点只能等发版,覆盖面增长慢。因为用户规则是这次需求的一部分而放弃。
- **全部迁成数据,删掉 compat.ts** —— 模型最统一,但 `take` 改指和尺寸判断这类函数式逻辑用纯选择器写不出来,硬塞进数据格式会让规则语法膨胀。
- **远程下发规则**(沉浸式翻译、kiss-translator 的做法)—— 修规则不用发版,但需要托管和版本兼容机制,还要面对各扩展商店对远程配置的审核。选择随扩展打包。

## 影响

- 「通用规则优先」的原则仍然成立:walker 的通用判定依旧是主路径,规则只是修正它。但新增一个站点的规则不再被视为缺陷。
- 坏规则两头拦:设置页保存时逐条校验选择器,无效的标红且不允许保存;运行时解析失败的选择器只跳过它自己,不影响其他选择器和其他规则,避免重演 #93(一条无效选择器让整页采集 0 个单元)。
- 用户规则按字段追加在内置规则之上,不整体替换,这样网站改版后内置规则的修复仍能送达用户;用户可以单独停用某个站点的内置规则。
- 判定顺序:站点黑名单 → 限定范围 → 数据规则的排除与保留原文(同一元素两者都命中时排除优先)→ compat.ts 代码层 → walker 通用判定。
- 内置规则由本项目自行编写。沉浸式翻译的规则仓库没有 LICENSE,read-frog 的内置规则来源不明,均不直接复用(见 [调研报告](../research/site-specialized-translation.md) 6.1 节)。
