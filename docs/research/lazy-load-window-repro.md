# 实测：长帖下半段漏翻是窗口漏翻，不是批次失败（#1010，父 #1003）

测量日期：2026-10-15。用途：#1003 的根因（“采集只做一次、观察器要等整页翻译成功才启动，两者之间加载出来的内容没人管”）是从代码时序推出来的。这里在真页面上分辨同一个症状的两个来源：窗口漏翻，还是某一批翻译失败。本票不改产品代码。

## 1. 方法

- 构建：origin/main（2.1.180，含 #1006 的 20 / 2000 切批与 #1007 的 content 侧闸门）。对照构建取 #1004 之前的 d9b4478（15 个一批、没有闸门），即用户报告时的形态。
- 驱动：Playwright 自带的 Chromium。Reddit 对无头浏览器只给一张“blocked by network security”拦截页，所以用有界面模式。界面语言 en-US，视口 1280×860，加载构建出的扩展。
- 引擎：
  - Google 替身：端到端套件的 `applyE2EMock`，每个请求固定延迟 470 ms。这个延迟取 #1006 实测的真实 Google 单次耗时；本机出口 IP 当天被 Google 限流（429），真实 Google 用不了。
  - 真实 Bing：作对照。
- 步骤：
  1. 打开页面，等 7 秒；
  2. 点悬浮球；
  3. 翻译期间每秒滚 900 像素，模拟用户边等边往下看；
  4. 悬浮球到完成态后停止滚动，再等 5 秒。
- 记录：
  - 页内用 MutationObserver 给每个条目（帖子或文章卡片）记下插入 DOM 的时刻；
  - 结束时看每个条目的标题有没有完成标记；
  - 提示框（toast）出现过的每一条文案；
  - 控制台里 `[PT]` 级别的错误，批次翻译失败会记在这里；
  - 从点击到悬浮球完成的总耗时。总耗时就是窗口的大小。
- 判据（#1003 票面）：
  - 窗口漏翻：报完成、控制台没有批次失败、漏掉的条目是窗口期间插入的。
  - 批次失败：控制台有 `[PT] 批次翻译失败`，或者出现失败提示。

## 3. 边滚边加载的页面

### 3.1 r/UTS 的最新帖子列表（Reddit 无限滚动）

|---|---|---|---|---|---|---|---|

| 翻译期间滚动（第二遍） | main / 替身 470 ms | 14.1 s | 同上 | **25 个，0 个有译文**（插入时刻 14.4 s，窗口 7.1 到 21.3 s） | — | 同上 | **0** |

| 翻译期间滚动 | main / 真实 Bing | 1.1 s | 27 个，27 个有译文 | 0（窗口太短，第一屏滚动还没触发加载） | — | “44 段已经是目标语言，没有插入译文” | 0 |

读法：
- 同一批帖子标题，在点击前加载（不滚动）与在完成后加载（观察器已启动）时都翻了；只在窗口期间加载时一个都没翻。标题本身是翻译单元，漏翻只与“什么时候进 DOM”有关。
- 窗口期间：悬浮球到完成态，控制台没有任何批次失败，唯一的提示是与漏翻无关的“1 段文字过长”，同 #1003 票面描述的症状一致：报完成，却有一整段原文。
- 窗口大小等于整页总耗时：替身 470 ms 下 14 秒，真实 Bing 下 1 秒。真实 Bing 那一次窗口里没加载出新帖子，所以没漏。翻译越慢漏得越多。
- 旧构建与 main 一样漏：这条与 #1000（批次排队超时）那条线无关，#1007 没有、也不该修好它。

## 4. 结论

**窗口漏翻，不是批次失败。** 依据：

1. 三组翻译期间滚动的运行（Reddit 列表两遍与旧构建一遍、dev.to 一遍），漏翻的条目全部是窗口期间插入的：25 / 25 / 25 / 26 个，没有一个有译文。
2. 点击前就在的条目与完成后插入的条目全部翻了（27 / 27、25 / 25、20 / 20、41 / 41）。
3. 所有运行控制台都没有 `[PT] 批次翻译失败`，也没有失败提示。悬浮球都到完成态。
4. 漏掉的单元数等于窗口期间插入的条目数，窗口等于整页总耗时（7.7 到 14.7 秒）。

所以 #1011 到 #1014 按 #1003 原设计做，不需要重新评估。票面那一帖今天不再懒加载评论，复现改在 Reddit 列表页与 dev.to 首页上完成。

## 5. 局限

- 测的是未登录视图。登录用户的评论树可能分批渲染，票面那一帖的原始现象没能在原帖上重现。
- 引擎延迟来自替身；真实 Google 的长尾只会让窗口更大。
- “点击前就在的帖子”在滚动后被 Reddit 的列表回收（移出 DOM），所以翻译期间滚动的那几行里这一列没有可数的数字；不滚动的对照里这 27 个全部有译文。

## 6. 补采集的轮间间隔（#1013）

#1013 让补采集一轮补完再查一次，查之前要等懒加载把下一批渲染出来。这一节量的是：滚到底之后，要过多久页面上才出现下一批条目。

方法：2026-10-15，同第 3 节的两个页面，未登录。滚到页面底部，从滚动那一刻开始计时，每 50 毫秒数一次条目数。记两个时刻：

- 首个新条目出现的时刻（下表“出现”）。
- 条目数不再变化的时刻（下表“渲染完”）。

| 页面 | 滚动前条目数 | 出现 | 渲染完 | 新增 |
|---|---|---|---|---|
| Reddit 列表 | 27 | 929 ms | 929 ms | 25 |
| Reddit 列表 | 52 | 1243 ms | 1243 ms | 25 |
| dev.to 首页 | 20 | 757 ms | **1429 ms** | 27 |
| dev.to 首页 | 47 | 390 ms | 390 ms | 14 |
| dev.to 首页 | 61 | 632 ms | 632 ms | 15 |
| dev.to 首页 | 76 | 467 ms | 467 ms | 15 |
| dev.to 首页 | 91 | 718 ms | 718 ms | 15 |
| dev.to 首页 | 106 | 788 ms | 788 ms | 15 |
| dev.to 首页 | 121 | 476 ms | 476 ms | 14 |
| dev.to 首页 | 135 | 720 ms | 720 ms | 15 |

Reddit 第三次滚动之后，列表开始回收（条目数从 77 掉到 50），之后不再出现新条目。这几次不计入上表。

读法：

- 最快一次是 390 ms。观察器的 300 ms 防抖作间隔，一次都接不住：查的时候下一批还没出现，补采集就会以为没有新内容而提前结束。
- 最慢一次是 1429 ms，在 dev.to 第一次滚动时：750 ms 出现第一批，1.4 s 才全部渲染完。

**定为 1500 毫秒**，覆盖全部 10 次的“渲染完”时刻。代价只落在确实补到了新内容的页面上：补采集第一轮紧接整页翻译，没有新单元就直接结束，不等。

**轮数封顶 3 轮**（票面建议值）。在持续加载的页面上，最多比原来多等两个间隔（3 秒）再报完成。第 3 轮之后的内容交给观察器。

量这组数的脚本只放在本机临时目录，没有进仓库。原始数据记在 #1013 的 PR 里。
